SLIDE 01 — What: Concise Technical Definitions

Messaging vs. Streaming

Messaging
A communication pattern where discrete messages are passed from producers to consumers via a broker. Focus is on reliable point-to-point or pub-sub delivery. Examples: RabbitMQ, ActiveMQ.
Streaming
Treats data as an unbounded, continuous sequence of events. Enables processing in real-time with concepts like event time, windowing, and stateful operations. Apache Kafka is a distributed event streaming platform, combining a high-performance broker with stream processing capabilities.

Kafka Ecosystem — Core Terminology

TermDefinition
BrokerA Kafka server that stores data and serves clients. A cluster consists of multiple brokers.
TopicA logical channel to which producers write and consumers read. Topics are partitioned.
PartitionAn ordered, immutable sequence of records. Each partition is replicated across brokers for fault tolerance.
ReplicationCopies of partitions (replicas) stored on multiple brokers. One replica is the leader; others are followers (ISR).
ISR (In-Sync Replicas)Set of replicas fully caught up with the leader. Only ISR members can become new leaders on failure.
Leader ElectionProcess of selecting a new partition leader when the current leader fails. Controlled by the Controller broker.
ProducerA client that publishes records to a topic. Configurable with acks, retries, and idempotence settings.
Consumer / GroupClients that subscribe to topics. Consumers in the same consumer group jointly share partitions — each partition assigned to exactly one consumer in the group.
OffsetA sequential ID assigned to each record within a partition. Consumers track their position via offsets.
Delivery SemanticsAt-most-once, at-least-once, exactly-once. Determined by producer acks, idempotence, and consumer offset commits.
ACKsacks=0 (no wait), acks=1 (leader write), acks=all (all ISR replicas acknowledge).
Replication FactorNumber of copies of each partition across the cluster.
Idempotent ProducerEnsures no duplicates due to retries, using a producer ID and sequence numbers.
Key-Based PartitioningProducer specifies a key; the same key always routes to the same partition, preserving order per key.
Ordering GuaranteesWithin a partition, records are strictly ordered. Across partitions, there is no global order.

SLIDE 02 — What: Kafka Applied — Payments as a Domain Example

Applying Kafka: Payments as a Domain Example

Transaction authorization, settlement, fraud detection, and reconciliation. Events such as PaymentAuthorized, PaymentCaptured, and RefundInitiated are published to Kafka topics for real-time downstream processing by services including the fraud engine, ledger service, and notification service.

Why Does Kafka Exist — Problem Statement

Traditional monolithic systems and point-to-point integrations suffer from the following:

  • Tight coupling — services directly call each other, leading to fragile dependencies.
  • Scalability bottlenecks — databases become choke points for high-throughput event processing.
  • Data loss risk — without durable storage, failures cause unrecoverable data loss.
  • Out-of-order processing — distributed systems often struggle to maintain event order.
  • Lack of replayability — once processed, events cannot be replayed for debugging or new consumers.
  • Streaming vs. batch — hard to support both real-time and batch processing from the same pipeline.

Kafka Solves These By Providing:

  • Decoupling via a publish-subscribe model
  • High throughput with horizontal scaling
  • Durability through replication and disk persistence
  • Ordering within partitions
  • Replayability via offset management and retention policies
  • Unified platform for real-time streams and batch integration

SLIDE 05 — How to Implement: High-Level Steps

5.1 Setting Up a Kafka Cluster

  1. Choose number of brokers (odd number, at least 3 for quorum).
  2. Configure server.properties: broker ID, listeners, log directories, and replication factor (e.g., 3).
  3. Start ZooKeeper or use KRaft mode (Kafka Raft) for metadata management — recommended for new clusters.
  4. Create topics with desired partitions and replication factor.

5.2 Producer Implementation

  1. Add the spring-kafka dependency to pom.xml.
  2. Configure ProducerFactory and KafkaTemplate.
  3. Define application.yml with bootstrap servers, key/value serializers, acks, retries, and idempotence settings.
  4. Inject KafkaTemplate and send messages with business keys. Handle async callbacks for success and failure.

5.3 Consumer Implementation

  1. Configure ConsumerFactory and KafkaListenerContainerFactory.
  2. Define application.yml with consumer group, offset reset policy, and key/value deserializers.
  3. Create @KafkaListener methods with topics and error handling.
  4. Implement idempotent processing and manual offset commits after successful processing.

5.4 Stream Processing (Optional)

  1. Use Kafka Streams DSL or Spring Cloud Stream.
  2. Define topologies with state stores, aggregations, and joins.

5.5 Exactly-Once Semantics

  1. Enable idempotent producer: enable.idempotence=true.
  2. Set acks=all and max.in.flight.requests.per.connection=5 (safe with idempotence enabled).
  3. Use transactions: initTransactions(), beginTransaction(), sendOffsetsToTransaction(), commitTransaction().
  4. Configure consumer: isolation.level=read_committed to read only committed messages.

SLIDE 06 — Kafka Architecture: Broker & Topic Internals

6.1 Broker Internals

A Kafka broker is a JVM process that manages:

  • Log segments — each partition is divided into segment files on disk. Segments are append-only and indexed for fast lookups.
  • Replication manager — handles leader/follower coordination, fetches from leaders, and manages the ISR set.
  • Controller — one broker acts as the controller, managing partition leader elections, topic creation, and cluster metadata. In KRaft mode, this role is merged with the metadata quorum.
  • Network layer — handles producer/consumer requests using NIO, with configurable thread pools.
  • Metadata cache — stores topic-partition assignments, broker liveness, and cluster state.

6.2 Topic-Partition Structure

  • A topic is a logical category. Physically, it is split into partitions — the unit of parallelism.
  • Each partition is an ordered, immutable log. Messages are assigned a sequential offset starting at 0.
  • Partitions are distributed across brokers for load balancing and fault tolerance.

6.3 Replication and ISR

  • Each partition has a replication factor (RF). Replicas are stored on different brokers.
  • Leader — handles all reads and writes for the partition.
  • Followers — pull messages from the leader. Considered in-sync if they have caught up within replica.lag.time.max.ms.
  • ISR — set of fully caught-up replicas. Only ISR members can be elected as leader on failure.
  • If all replicas are out of sync, unclean.leader.election.enable controls whether a non-ISR replica can become leader (risks data loss — set to false in production).

6.4 Leader Election

  • Triggered by broker failure, controlled removal, or partition reassignment.
  • The controller monitors ZooKeeper/KRaft for broker heartbeats.
  • When a leader disappears, the controller selects a new leader from the ISR, ensuring the new leader has the most up-to-date data.

6.5 Producers

  • Producers choose which partition to write to (round-robin if no key, or hash of key for ordered delivery).
  • Records are batched to improve throughput before being sent to the broker.
  • Acknowledgment levels (acks) determine the durability guarantee per message.
  • Idempotent producers assign a producer ID and sequence numbers to detect and reject duplicates at the broker.

SLIDE 07 — Kafka Architecture: Consumers, KRaft & Cluster Diagram

6.6 Consumers and Consumer Groups

  • Consumers read from partitions; each consumer in a group is assigned a subset of partitions (exactly one consumer per partition within a group).
  • Offsets are committed to Kafka's internal topic __consumer_offsets.
  • Group coordination: one consumer acts as group leader, handling partition assignment when members join or leave (triggering a rebalance).

6.7 ZooKeeper vs. KRaft

  • Legacy Kafka uses ZooKeeper for cluster metadata: broker registry, topic configurations, and controller election.
  • KRaft (Kafka Raft) replaces ZooKeeper with an internal Raft quorum, simplifying operations and improving startup time.
  • In production, KRaft is recommended for all new clusters (available since Kafka 2.8, production-ready since Kafka 3.3).

SLIDE 09 — Failure Modes: Data Loss, Duplicates & Out-of-Order

9.1 Data Loss

Scenario

Producer sends a message with acks=0. Broker crashes before writing to disk. Message is permanently lost — no retry, no recovery.

// INCORRECT: Producer with acks=0 — fire and forget, no durability
@Bean
public ProducerFactory<String, PaymentEvent> producerFactory() {
    Map<String, Object> props = new HashMap<>();
    props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
    props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
    props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, JsonSerializer.class);
    props.put(ProducerConfig.ACKS_CONFIG, "0"); // <-- no acknowledgement, no guarantees
    return new DefaultKafkaProducerFactory<>(props);
}
Effect: If broker crashes after accepting but before replicating, the message is lost permanently. In payments, this equals untracked transactions — a regulatory violation.

9.2 Duplicate Messages

Scenario

Producer retries after a timeout, but the first attempt actually succeeded (network hiccup). A duplicate message is sent and processed twice by the consumer.

// INCORRECT: Idempotence disabled with high retry count
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, false);
props.put(ProducerConfig.RETRIES_CONFIG, 10);
Effect: Duplicate events lead to double-counting in payment systems (e.g., debiting a customer twice).

9.3 Out-of-Order Messages

Scenario

Two messages with the same key sent to the same partition. First message is delayed due to retry; the second arrives and is processed first.

// INCORRECT: Multiple in-flight requests with retries and no idempotence
props.put(ProducerConfig.MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION, 5);
props.put(ProducerConfig.RETRIES_CONFIG, 10);
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, false);
Effect: Messages for the same paymentId processed out of order — causing incorrect state, e.g., settlement before authorization.

SLIDE 10 — Failure Modes: Offset Commits, Availability & Poison Pills

9.4 Consumer Offset Commit Issues

Scenario

Consumer processes a message but crashes before committing the offset. After rebalance, another consumer re-processes the same message (at-least-once). If processing is not idempotent, duplicates occur.

// INCORRECT: Auto-commit fires after poll(), not after processing completes
@KafkaListener(topics = "payment-events", groupId = "payment-group")
public void listen(PaymentEvent event) {
    // Process event — auto-commit may fire before this completes
    // If crash occurs between poll and processing: message re-consumed
    // If auto-commit fires before processing: message lost on crash
}
Effect: Auto-commit fires after poll(), not after processing. Crash between poll and processing completion causes either message loss or duplicate processing depending on timing.

9.5 Leader Election and Availability

Scenario

Broker hosting the partition leader goes down. During election, the partition is unavailable for writes if min.insync.replicas is not satisfied by the remaining ISR.

Root Cause: min.insync.replicas set too high relative to the replication factor, or all replicas simultaneously fall out of sync due to a network partition.

9.6 Consumer Lag and Rebalancing

Scenario

Consumers take too long to process messages, causing growing lag. Rebalancing during long processing windows may cause duplicate processing or stop-the-world pauses across all consumers in the group.

Effects:
  • Increased end-to-end latency and potential message expiry
  • Under-provisioned consumers or slow processing logic
  • Hot partitions — one partition receives disproportionate traffic due to poor key selection
  • max.poll.interval.ms exceeded → consumer ejected from group → rebalance storm

9.7 Poison Pills

Scenario

A malformed message causes the consumer to throw an exception repeatedly, stalling the entire partition indefinitely.

Incorrect Handling: No error handling or dead-letter topic configured. Consumer enters an infinite retry loop, blocking all subsequent messages on that partition.

SLIDE 11 — Root Cause Analysis

Why It Fails: Detailed Root Causes

10.1 Data Loss

Cause: acks=0 or acks=1 combined with unclean leader election. If the leader fails before replicating to followers, and a non-ISR replica becomes leader, data is permanently lost. Root: Trade-off of performance over durability.

10.2 Duplicates

Cause: Producer retries without idempotence enabled. The broker accepted the first write but the producer did not receive an acknowledgement. The second attempt creates a duplicate. Root: Lack of exactly-once semantics on the producer side.

10.3 Out-of-Order Messages

Cause: Multiple in-flight requests with retries enabled. If the first request fails and is retried, but the second succeeds first, the retried first message arrives out of sequence. Root: Violating the max.in.flight=1 constraint without enabling idempotence.

10.4 Offset Commit Issues

Cause: Auto-commit triggers after poll(), not after processing completes. If processing fails after offset commit, the message is lost. If the consumer crashes before auto-commit, the message is re-consumed. Root: Misunderstanding of commit timing semantics.

10.5 Unavailability

Cause: All replicas of a partition are out of sync, or min.insync.replicas exceeds the current ISR count. Writes fail with NotEnoughReplicasException. Root: Network partition, broker overload, or misconfiguration.

10.6 Consumer Lag

Cause: Under-provisioned consumers, slow processing logic, or hot partitions receiving disproportionate traffic due to poor key selection. Root: Uneven load distribution or insufficient consumer parallelism.

10.7 Poison Pills

Cause: Invalid data format, missing required fields, or deserialization errors. Lack of schema validation at the producer side. Root: Absence of schema registry or input validation before publishing.

SLIDE 12 — Correct Approach & Key Principles

Patterns to Mitigate Failure

Production-Grade Configuration Checklist

  • Use acks=all and enable.idempotence=true on all producers
  • Set min.insync.replicas=2 for strong durability guarantees
  • Use manual offset commits after successful processing only
  • Implement idempotent consumers — store processed IDs in a DB with a unique constraint
  • Use dead-letter topics (DLT) for unprocessable messages (poison pills)
  • Monitor consumer group lag and set up alerts on JMX / Prometheus metrics
  • Choose partitioning keys that ensure order AND even distribution (e.g., paymentId)
  • Plan for partition count increases — design consumers to handle rebalancing gracefully

Key Principles

CAP Theorem

Kafka is an AP system (Availability + Partition Tolerance) but can be tuned for consistency with acks=all and min.insync.replicas. In practice, it provides strong consistency within the ISR.

Idempotency — Producer and Consumer

Producer idempotence ensures no duplicates from retries (producer ID + sequence numbers assigned by broker). Consumer idempotence ensures safe reprocessing by checking a processed-ID table before executing business logic.

Ordering Guarantee

Within a partition, order is preserved if the producer sends in sequence and the partitioner respects the key. Global order requires a single partition — this sacrifices parallelism and should be avoided in high-volume payment systems.

Exactly-Once Semantics (EOS)

Achieved via idempotent producer + Kafka transactions + consumer isolation.level=read_committed. Ensures each message is processed exactly once end-to-end. Critical for payment ledger updates.

Log Compaction

Kafka can retain only the latest value for each key (compacted topics). Useful for state snapshots — e.g., storing the latest account balance or configuration values.

Choosing Between At-Least-Once + Idempotent Consumer vs. Exactly-Once Transactions

  • At-least-once + idempotent consumer — simpler, widely used, sufficient for most payment workflows. Small overhead from duplicate checking in the database.
  • Exactly-once transactions — required when the DB write and Kafka send must atomically succeed or fail together. Higher complexity and ~2–3× latency overhead.

      value-deserializer: org.springframework.kafka.support.serializer.JsonDeserializer
      properties:

        spring.json.type.mapping: paymentEvent:com.example.dto.PaymentEvent
      auto-offset-reset: earliest          # If no committed offset, start from beginning
      enable-auto-commit: false            # Commit manually after processing — critical
      isolation-level: read_committed      # Read only committed messages (EOS consumers)
    listener:
      type: batch                          # Listen in batches
      ack-mode: manual_immediate           # Acknowledge as soon as manual ack is called
      concurrency: 3                       # Consumer threads (match partition count)

Why These Settings Matter

  • acks=all — message not considered sent until all ISR replicas acknowledge. Prevents data loss if leader crashes immediately after write.
  • enable-idempotence=true with max.in.flight=5 — guarantees ordering and deduplication at the broker, even with retries.
  • enable-auto-commit=false — gives precise control over offset commits; prevents message loss and uncontrolled duplicates.
  • isolation.level=read_committed — consumers only see messages from committed transactions; prevents reading dirty/uncommitted data.
  • concurrency=3 — creates three Kafka consumer threads; tune to match the number of partitions for maximum parallelism.

13.4 Producer Service with Async Callbacks

package com.example.producer;

import com.example.dto.PaymentEvent;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.kafka.support.SendResult;
import org.springframework.stereotype.Service;

import java.util.concurrent.CompletableFuture;

@Service
public class PaymentEventProducer {
    private static final Logger logger = LoggerFactory.getLogger(PaymentEventProducer.class);
    private final KafkaTemplate<String, PaymentEvent> kafkaTemplate;

    public PaymentEventProducer(KafkaTemplate<String, PaymentEvent> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    public void sendPaymentEvent(String key, PaymentEvent event) {
        CompletableFuture<SendResult<String, PaymentEvent>> future =
                kafkaTemplate.send("payment-events", key, event);

        future.whenComplete((result, ex) -> {
            if (ex == null) {
                logger.info("Sent event: key=[{}], partition=[{}], offset=[{}]",
                        key,
                        result.getRecordMetadata().partition(),
                        result.getRecordMetadata().offset());
            } else {
                logger.error("Unable to send event key=[{}]: {}", key, ex.getMessage(), ex);
                // Options:
                // 1. Retry manually (if not relying on auto-retries)
                // 2. Send to dead-letter topic
                // 3. Throw to trigger upstream transaction rollback
            }
        });
    }
}

Why Async Callbacks?

  • KafkaTemplate.send() returns a CompletableFuture — non-blocking by design.
  • whenComplete logs the success details (partition + offset) or routes failures to appropriate handlers.
  • Never call .get() (synchronous send) in the critical payment path — it blocks the thread and severely reduces throughput.
  • The idempotent producer configuration ensures automatic retries do not cause duplicates at the broker level.

SLIDE 15 — Production Code: Consumer with Manual Commit & Idempotency

13.5 Consumer with Idempotent Processing

package com.example.consumer;

import com.example.dto.PaymentEvent;
import org.apache.kafka.clients.consumer.ConsumerRecord;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.kafka.support.Acknowledgment;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

import javax.persistence.EntityManager;
import java.util.UUID;

@Component
public class PaymentEventConsumer {
    private static final Logger logger = LoggerFactory.getLogger(PaymentEventConsumer.class);
    private final EntityManager entityManager;

    public PaymentEventConsumer(EntityManager entityManager) {
        this.entityManager = entityManager;
    }

    @KafkaListener(topics = "payment-events", groupId = "payment-group")
    @Transactional  // DB update + idempotency marker committed atomically
    public void consume(ConsumerRecord<String, PaymentEvent> record, Acknowledgment ack) {
        try {
            PaymentEvent event = record.value();
            logger.info("Consumed: key={}, partition={}, offset={}",
                    record.key(), record.partition(), record.offset());

            // IDEMPOTENCY CHECK: Have we already processed this paymentId?
            if (isProcessed(event.getPaymentId())) {
                logger.info("Duplicate detected for paymentId={}, skipping", event.getPaymentId());
                ack.acknowledge();  // Still commit offset — event is handled
                return;
            }

            // Business logic (e.g., update ledger balance)
            processPayment(event);

            // Mark as processed IN THE SAME transaction as the business logic
            markAsProcessed(event.getPaymentId());

            // Manual offset commit — ONLY after successful processing and DB commit
            ack.acknowledge();

        } catch (Exception e) {
            logger.error("Error processing key={}, offset={}. Routing to DLT.",
                    record.key(), record.offset(), e);
            // DO NOT ack — let the error handler manage retry or DLT routing
            throw new RuntimeException(e);
        }
    }

    private boolean isProcessed(UUID paymentId) {
        return entityManager.find(ProcessedPayment.class, paymentId) != null;
    }

    private void markAsProcessed(UUID paymentId) {
        entityManager.persist(new ProcessedPayment(paymentId, Instant.now()));
    }

    private void processPayment(PaymentEvent event) {
        // Business logic: update account balance, ledger entry, etc.
    }
}

Why This Pattern Guarantees Exactly-Once Processing

  • Manual commit via Acknowledgment.acknowledge() ensures offsets are committed only after processing completes and the idempotency check passes.
  • Idempotency is achieved by persisting processed paymentIds in the DB with a unique constraint. Duplicate events (after rebalance or retry) are detected and silently skipped.
  • @Transactional ensures the business logic update AND the processed marker are committed atomically. If the DB commit fails, the exception is thrown, the offset is not committed, and the consumer retries.
  • This pattern delivers exactly-once processing = at-least-once delivery + idempotent consumer logic.

13.6 Error Handler with Dead Letter Topic (DLT)

package com.example.config;

import org.apache.kafka.clients.consumer.ConsumerRecord;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.kafka.listener.CommonErrorHandler;
import org.springframework.kafka.listener.MessageListenerContainer;
import org.springframework.kafka.support.serializer.DeserializationException;
import org.springframework.kafka.core.KafkaTemplate;

public class KafkaErrorHandler implements CommonErrorHandler {
    private static final Logger logger = LoggerFactory.getLogger(KafkaErrorHandler.class);
    private final KafkaTemplate<String, Object> kafkaTemplate;

    public KafkaErrorHandler(KafkaTemplate<String, Object> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    @Override
    public boolean handleOne(Exception thrownException, ConsumerRecord<?, ?> record,
                             org.apache.kafka.clients.consumer.Consumer<?, ?> consumer,
                             MessageListenerContainer container) {
        if (thrownException instanceof DeserializationException) {
            // Deserialization errors are UNRECOVERABLE — route to DLT immediately
            logger.error("Deserialization error for record: {}", record, thrownException);
            sendToDLT(record, thrownException);
            return true;  // Mark handled — prevents infinite retry loop
        }
        return false;  // Let retry mechanism handle (e.g., SeekToCurrentErrorHandler + backoff)
    }

    private void sendToDLT(ConsumerRecord<?, ?> record, Exception e) {
        DeadLetterEvent dle = new DeadLetterEvent(
                record.topic(), record.partition(), record.offset(),
                record.key() != null ? record.key().toString() : null,
                record.value(), e.getMessage()
        );
        kafkaTemplate.send("payment-events-dlt", dle);
        logger.info("Routed poison pill to DLT: topic={}, partition={}, offset={}",
                record.topic(), record.partition(), record.offset());
    }
}
Deserialization errors are unrecoverable. Routing to the DLT prevents the consumer from stalling indefinitely on a malformed message. The DLT is monitored for manual intervention and schema validation fixes. Recoverable errors (e.g., transient DB unavailability) are left for the retry mechanism with exponential backoff.

13.7 Transactional Producer — Exactly-Once Across Database and Kafka

@Service
public class TransactionalPaymentService {
    private final KafkaTemplate<String, PaymentEvent> kafkaTemplate;

    public TransactionalPaymentService(KafkaTemplate<String, PaymentEvent> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    // Producer must be configured with transactional.id (unique per producer instance)
    @Transactional(transactionManager = "kafkaTransactionManager")
    public void processAndSend(PaymentEvent event) {
        // 1. Perform DB update (e.g., debit account balance)
        // accountRepository.debit(event.getUserId(), event.getAmount());

        // 2. Send Kafka message — committed ONLY if DB update succeeds
        kafkaTemplate.send("payment-events", event.getPaymentId().toString(), event);

        // If DB update fails → Kafka transaction rolls back → message is NOT committed
        // Consumers with isolation.level=read_committed will never see uncommitted messages
    }
}

When to Use Kafka Transactions

  • @Transactional with a Kafka transaction manager ensures the Kafka send is part of the same transaction as the DB operation.
  • Producer must have transactional.id configured (unique per producer instance) to enable EOS.
  • Consumers with isolation.level=read_committed only see messages after the transaction commits.
  • This pattern is required when a DB update and Kafka event must atomically succeed or fail together — typical in payment ledger updates.
  • Trade-off: ~2–3× latency overhead vs. at-least-once. Use only when EOS across DB and Kafka is strictly mandated.

Step-by-Step Walkthrough

  1. Producer assigns a producer ID and sequence number to each message batch — broker detects and rejects any duplicates from retries.
  2. Broker leader appends to its local log, replicates to ISR followers, and acknowledges only after all ISR confirm.
  3. Consumer polls a batch of records and begins a database transaction for atomic processing.
  4. Idempotency check queries the DB for the processed marker; duplicate events are silently committed without re-executing business logic.
  5. Manual offset commit happens only after the DB transaction commits successfully — guaranteeing exactly-once end-to-end.
  6. On leader failure — the metadata quorum elects a new leader from the ISR; the consumer transparently resumes polling with no data loss.

SLIDE 18 — Anti-Patterns in Production Engineering (Part 1)

Common Mistakes — 15.1 to 15.6

15.1 Using Default Producer Settings

Mistake: Not explicitly setting acks=all or enable.idempotence=true, leading to data loss and duplicates in production.

Fix: Always configure production-grade settings explicitly. Never rely on defaults for financial systems.

15.2 Relying on Auto-Commit

Mistake: enable-auto-commit=true with ack-mode=RECORD. Messages may be committed before processing completes — a crash results in silent message loss.

Fix: Disable auto-commit. Use Acknowledgment.acknowledge() manually after successful processing.

15.3 Ignoring Consumer Rebalance

Mistake: No rebalance listener configured. Pending uncommitted offsets are lost during rebalance, causing duplicate processing on restart.

Fix: Implement ConsumerAwareRebalanceListener and commit pending offsets in onPartitionsRevoked().

15.4 Not Handling Poison Pills

Mistake: Allowing a deserialization exception to halt the consumer indefinitely. All subsequent messages on that partition are blocked.

Fix: Configure CommonErrorHandler with dead-letter topic routing for unrecoverable deserialization errors.

15.5 Assuming Partition Count Is Static

Mistake: Hardcoding partition count without planning for scaling. Adding partitions later breaks key-based ordering for newly produced messages.

Fix: Design for dynamic partition additions. Ensure consumers handle rebalancing gracefully via rebalance listeners.

15.6 Overusing Transactions

Mistake: Wrapping every Kafka send in a transaction, causing a 2–3× latency penalty unnecessarily.

Fix: Use transactions only when exactly-once semantics across multiple topics or a database update is strictly required.

SLIDE 19 — Anti-Patterns in Production Engineering (Part 2)

15.7 Improper Key Selection

Mistake 1: Using a key with extremely high cardinality causes many partitions to be underutilised or data to be skewed toward a few hot partitions.
Mistake 2: Using no key results in round-robin assignment, which loses all ordering guarantees for related events.

Fix: Choose a business key that both preserves event order and distributes load evenly. For payments: paymentId or accountId.

15.8 Not Monitoring Consumer Lag

Mistake: Assuming consumers keep up with producers without instrumentation. Silent lag buildup causes SLA breaches and eventual message expiry.

Fix: Set up consumer lag metrics and alerts. Use kafka-consumer-groups.sh --describe or Prometheus/Grafana with Kafka JMX metrics.

15.9 Misconfiguring max.poll.records and max.poll.interval.ms

Mistake: Setting max.poll.records too high. If processing a large batch exceeds max.poll.interval.ms, the broker considers the consumer dead and triggers a rebalance storm.

Fix: Tune based on expected processing time per record. Rule of thumb: max.poll.records × avg_processing_time_ms << max.poll.interval.ms.

15.10 Using Synchronous Send in the Critical Path

Mistake: Calling kafkaTemplate.send().get() — blocks the thread until the broker responds. Throughput drops from thousands per second to tens per second.

Fix: Use async send with whenComplete callbacks or CompletableFuture composition. Synchronous send is only appropriate in batch jobs where latency is not a concern.

Platform Recommendation — Applied to a Payments Context

  • Apache Kafka is the default choice for payment event streaming: high throughput, exactly-once semantics, full replay capability, and mature Java/Spring ecosystem.
