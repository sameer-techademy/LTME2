Module 1 · Slide 1 — Schema Registry — What & Why

What: Concise Technical Definition

Schema Registry is a distributed storage layer for Avro, JSON Schema, or Protobuf schemas that enforces a schema contract for Kafka messages. It stores versioned schemas, assigns a unique ID to each schema, and ensures that producers and consumers adhere to compatibility rules when schemas evolve.

Avro is a binary serialization format with a schema embedded in the message (or referenced by ID). It provides a compact wire size and strong typing.

Why Does It Exist

Without schema enforcement, producers and consumers silently drift apart — a field rename or type change causes downstream deserialization failures, data corruption, or silent nulls. Schema Registry prevents this by:

  • Rejecting incompatible schema changes at registration time.
  • Ensuring all messages are self-describing via a schema ID embedded in each message.
  • Allowing controlled evolution — adding or removing optional fields — without breaking existing clients.

When to Use It

  • Any production Kafka topic shared across multiple services.
  • When schemas need to evolve without stopping or redeploying consumers.
  • For high-throughput systems where compact binary encoding (Avro) reduces network and storage costs.
  • In regulated environments where data lineage and auditability are required.

Where to Use It — Architectural Layers

Producer
Serializers interact with Schema Registry to resolve schema IDs before publishing messages to Kafka.
Consumer
Deserializers fetch the schema by ID to reconstruct strongly-typed objects on receipt.
CI/CD
Schema registration and compatibility checks are automated as a pipeline gate before deployment.
Governance
Centralised schema management with versioning, subject-level access control, and audit history.

How to Implement — High-Level Steps

  1. Deploy Schema Registry (Confluent or open-source) alongside your Kafka cluster.
  2. Define Avro schemas (.avsc files) within your project source tree.
  3. Configure Spring Boot producers with KafkaAvroSerializer and auto.register.schemas=false.
  4. Configure consumers with KafkaAvroDeserializer and specific.avro.reader=true.
  5. Set compatibility mode on subjects (e.g., BACKWARD or BACKWARD_TRANSITIVE).
  6. In CI, check compatibility (POST /compatibility) before registering new schema versions.

Scenario: Field Rename Causes Silent Data Corruption

Problem

A service renames the field amt to amount. All downstream consumers break silently — no exception is raised, but the analytics pipeline ingests NaN for three days before the issue is identified.

Solution

With Schema Registry configured in BACKWARD mode, the renamed field is detected as an incompatible change and the registration is rejected at the CI stage. Alternatively, adding the new field as optional with a default allows consumers on the old schema to continue reading messages — seeing null for the new field — without any downtime.

Module 1 · Slide 3 — Failure Modes, Root Cause & Correct Approach

What Can Go Wrong — Failure Modes

  • Raw JSON strings without schema enforcement — field rename breaks consumers silently with no error at runtime.
  • auto.register.schemas=true in production — any local execution can register new schema versions, bypassing code review.
  • An incompatible FULL_TRANSITIVE change — breaks all historical consumers simultaneously.
  • Using GenericRecord instead of a generated class — loss of compile-time type safety; errors surface at runtime.
  • Omitting specific.avro.reader=true — the consumer receives a GenericRecord; casting fails and the application crashes.

Root Cause Analysis

Silent Breakage

Without a schema contract, the producer and consumer are coupled through an implicit, undocumented understanding of the message format. Any change on one side is invisible to the other until a runtime deserialization failure occurs in production.

  • Uncontrolled registration: With auto.register.schemas=true, a developer running a test locally can inadvertently register a breaking schema version directly against the production registry.
  • Misconfigured compatibility mode: Setting mode to NONE disables all evolution checks, allowing any change regardless of impact on existing consumers.
  • Missing defaults for new fields: Adding a required field with no default makes every existing message on the topic unreadable by the new schema version.

Correct Approach — Architectural Pattern

Schema Evolution Rules

  • Use BACKWARD or BACKWARD_TRANSITIVE for most production topics — new consumers can read messages written with older schemas.
  • CI/CD gating: Run POST /compatibility in the pipeline; never auto-register schemas in any environment above development.
  • Idempotent evolution: Always add new fields as optional with a default (["null","string"] with "default":null). Never remove fields — deprecate them and retain them with a default.
  • Code generation: Generate Java classes from .avsc files at build time to enforce type safety at compile time, not at runtime.

Key Principles

  • Compatibility modes — BACKWARD, FORWARD, FULL — define the contract for how producers and consumers may evolve independently over time.
  • The schema ID embedded in each message header enables self-describing data without sending the full schema on every message.
  • Client-side schema caching reduces round trips to the registry to a single lookup per schema ID per client lifecycle.

Module 2 · Slide 1 — Kafka Security — What, Why & How

What: Concise Technical Definition

Kafka security is composed of three complementary layers:

  • Encryption (TLS) — protects data in transit between clients and brokers.
  • Authentication — verifies the identity of clients and brokers using SSL mutual TLS (mTLS) or SASL mechanisms.
  • Authorization (ACLs) — controls which authenticated principals can perform which operations on which resources (topics, consumer groups, cluster).

Why Does It Exist

Without security controls, any service on the network can connect to Kafka, read sensitive data, or inject fraudulent events. Compliance requirements mandate encryption at rest and in transit, along with verifiable access control. Mutual TLS ties client identity to a certificate, enabling fine-grained, service-level ACL enforcement.

When to Use It

  • Any production cluster handling PII, financial data, or regulated information.
  • Multi-tenant environments where teams require isolation between topics and consumer groups.
  • When network segmentation alone is insufficient — security in depth is required.

Where to Apply

Broker
Configure SSL listeners on each broker; disable all plaintext ports in production.
Client
Each service application configures a keystore (client identity) and truststore (CA trust) to participate in mTLS.
Operations
Manage certificate rotation schedules and ACL definitions per principal across the cluster lifecycle.

How to Implement — High-Level Steps

  1. Generate a Certificate Authority (CA) and issue broker and client certificates signed by it.
  2. Configure broker server.properties with an SSL listener, keystore and truststore paths, and ssl.client.auth=required.
  3. Configure each client application with its own keystore (identity) and truststore (CA verification).
  4. Set authorizer.class.name and define ACLs per principal. The principal is derived from the certificate Common Name (CN).
  5. Remove all plaintext listeners so no unencrypted path remains open on the cluster.

Problem

A security audit reveals a Kafka cluster with no encryption or authentication. Any service on the internal network can connect, consume sensitive event data, or produce messages into any topic. The cluster is non-compliant with data protection regulations.

Module 2 · Slide 3 — Failure Modes, Root Cause & Correct Approach

What Can Go Wrong — Failure Modes

  • Leaving plaintext port 9092 open alongside the SSL port — provides a complete security bypass for any client that knows the port.
  • Broker's self-signed certificate not present in the client truststore — the SSL handshake fails for all connecting clients.
  • ssl.endpoint.identification.algorithm set to empty — disables hostname verification; man-in-the-middle attacks become feasible.
  • No ACLs defined after enabling mTLS — authenticated clients have unrestricted access to all topics and consumer groups.
  • Keystore passwords hardcoded in application.yml — credentials are committed to version control and exposed.

Root Cause Analysis

  • Plaintext port left open: Misconfiguration or oversight during initial setup; security controls applied inconsistently across the listener configuration.
  • Truststore missing CA: The client cannot verify the broker's certificate chain, resulting in a TLS handshake failure on every connection attempt.
  • Hostname verification disabled: The broker's certificate Subject Alternative Name (SAN) is not validated against the advertised listener address, allowing certificate substitution.
  • No ACLs defined: Authentication establishes identity; without authorization rules, identity does not restrict access to any resource.

Correct Approach — Architectural Pattern

Defense in Depth

  • Encrypt, authenticate, authorize — all three layers must be active simultaneously. Enabling two out of three is insufficient.
  • Single SSL listener — configure only the SSL endpoint; remove all plaintext listeners from the broker configuration.
  • Certificate lifecycle management — use short-lived certificates (90-day rotation), automated via internal tooling or a secrets manager.
  • Principle of least privilege — define ACLs per principal with the minimum set of operations required for that service to function.

Key Principles

  • Mutual TLS (mTLS): Both parties present and verify certificates before any data is exchanged — identity is cryptographic, not network-based.
  • Principal: The client identity is extracted from the certificate's Common Name (CN) and used as the subject for ACL lookups.
  • Hostname verification: Prevents man-in-the-middle attacks by requiring the certificate SAN to match the broker's advertised hostname.
  • ACL evaluation: Kafka checks the tuple (principal, resource, operation) against the stored ACL list for every incoming request.

@Configuration
public class KafkaSecurityConfig {

    @Bean
    public ProducerFactory<String, String> secureProducerFactory(
            @Value("${kafka.ssl.keystore-location}")  String keystoreLoc,
            @Value("${kafka.ssl.keystore-password}")  String keystorePass,
            @Value("${kafka.ssl.key-password}")       String keyPass,
            @Value("${kafka.ssl.truststore-location}") String truststoreLoc,
            @Value("${kafka.ssl.truststore-password}") String truststorePass) {

        Map<String, Object> props = new HashMap<>();
        props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka-broker1.example.com:9093");
        props.put(CommonClientConfigs.SECURITY_PROTOCOL_CONFIG, "SSL");
        props.put(SslConfigs.SSL_KEYSTORE_LOCATION_CONFIG, keystoreLoc);
        props.put(SslConfigs.SSL_KEYSTORE_PASSWORD_CONFIG, keystorePass);
        props.put(SslConfigs.SSL_KEY_PASSWORD_CONFIG, keyPass);
        props.put(SslConfigs.SSL_TRUSTSTORE_LOCATION_CONFIG, truststoreLoc);
        props.put(SslConfigs.SSL_TRUSTSTORE_PASSWORD_CONFIG, truststorePass);
        props.put(SslConfigs.SSL_ENDPOINT_IDENTIFICATION_ALGORITHM_CONFIG, "https");
        props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class);
        props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class);

        return new DefaultKafkaProducerFactory<>(props);
    }
}

Module 3·Slide 1 of 5·Event-Driven Design

Module 3 · Slide 1 — Events vs Commands, Pub-Sub & Sagas

What: Concise Technical Definitions

Event
A fact that has occurred in the past (e.g., PaymentCreated). Events are immutable and broadcast to any interested parties. The publisher has no knowledge of who consumes the event.
Command
A request for a specific action to be performed (e.g., ReserveStock). Commands have an explicit target and expect a response — success or failure.
Pub-Sub
A messaging pattern where publishers send events to topics and multiple subscribers — each in their own consumer group — receive all events independently.
Choreography
A decentralized coordination style where services react to events and emit their own events, with no central coordinator directing the flow.
Orchestration
A central service — the orchestrator — directs other services by sending commands and handling their responses, maintaining the overall workflow state.
Saga
A sequence of local transactions where each step publishes an event triggering the next step. If a step fails, compensating transactions undo previous steps to restore consistency.

Why Does It Exist

Tight coupling via synchronous REST calls leads to cascading failures, low resilience, and tangled service dependencies. Event-driven architectures decouple services, improve scalability, and enable independent evolution. Sagas provide data consistency across service boundaries without distributed transactions (2PC), which are impractical in microservice environments.

When to Use Each Pattern

  • Events: Broadcasting facts to multiple independent consumers — audit logs, analytics, notifications, derived state updates.
  • Commands: Point-to-point requests where a specific service must act; prefer synchronous channels with a reply unless asynchrony is a requirement.
  • Choreography: Simple, linear flows where each service can evolve and operate independently of others.
  • Orchestration: Complex flows with conditional branches, error handling paths, or strict ordering requirements.
  • Sagas: Any business process spanning multiple services that must maintain eventual consistency.

How to Implement — High-Level Steps

  1. Identify domain events using past-tense naming (e.g., OrderPlaced, PaymentApproved).
  2. Design a topic per event type or per aggregate boundary.
  3. Each consuming service maintains its own consumer group to receive all events independently (true fan-out).
  4. For sagas: each step performs a local transaction and publishes an event; define compensating transactions for every state-mutating step.
  5. Propagate a correlation ID in Kafka message headers to trace the complete flow across services.

Module 3·Slide 3 of 5·Event-Driven Design

Module 3 · Slide 3 — Failure Modes, Root Cause & Correct Approach

What Can Go Wrong — Failure Modes

  • Publishing commands instead of events — the producer implicitly knows the consumer, re-introducing tight coupling through the message broker.
  • All consuming services sharing one consumer group — Kafka distributes events across consumers in the group; not all services receive every event.
  • No compensating transactions defined — a partial saga leaves data permanently inconsistent when any step fails.
  • Choreography without distributed tracing — debugging a multi-hop flow across services becomes an intractable forensic exercise.
  • Event names in imperative tense (ProcessPayment) — ambiguous intent; blurs the semantic boundary between events and commands.

Root Cause Analysis

  • Command over event: The producer expects a specific consumer to act, violating the decoupled pub-sub model and coupling services through message content.
  • Shared consumer group: Kafka's partition assignment allocates each partition to exactly one consumer per group. Multiple services sharing a group will not all receive every event — fan-out requires independent consumer groups.
  • Missing compensation: Developers focus on the success path and omit undo logic, assuming downstream steps always succeed.
  • No correlation ID: Without a trace ID propagated in headers, log entries across services cannot be connected to a single originating transaction.

Correct Approach — Architectural Pattern

Event-First Design

  • Model business facts, not service instructions. Use past-tense event names that describe what occurred, not what should be done next.
  • One consumer group per service to guarantee every interested service receives every event (complete fan-out).
  • Saga pattern: Every step that mutates state must be idempotent and must have a clearly defined compensating transaction.
  • Correlation IDs: Propagate a trace ID in Kafka message headers on every publish; read and re-propagate on every consume.

Key Principles

  • Idempotency: Event handlers must be safe to retry — processing the same event multiple times must yield the same state outcome.
  • Eventual consistency: Sagas accept temporary inconsistency between services during execution but guarantee correctness once all saga steps complete.
  • Compensating transactions: Must be explicitly designed, implemented, and tested for every step that mutates shared or durable state.

Independent Consumer — Inventory Service (own consumer group)

@Component
public class InventoryEventHandler {
    private final InventoryRepository repo;
    private final KafkaTemplate<String, String> kafkaTemplate;
    private final ObjectMapper om;

    @KafkaListener(topics = "payment.created", groupId = "inventory-group")
    public void handle(String message, Acknowledgment ack) throws Exception {
        var event = om.readValue(message, PaymentCreatedEvent.class);
        try {
            repo.reserveIfPossible(event.orderId(), event.paymentId()); // idempotent upsert
            var stockReserved = new StockReservedEvent(event.orderId(), event.paymentId());
            kafkaTemplate.send("stock.reserved", event.paymentId(),
                om.writeValueAsString(stockReserved));
            ack.acknowledge();
        } catch (OutOfStockException e) {
            // Business failure — publish a domain event, do not throw
            var failed = new StockReservationFailedEvent(event.orderId(), event.paymentId());
            kafkaTemplate.send("stock.reservation-failed", event.paymentId(),
                om.writeValueAsString(failed));
            ack.acknowledge();
        }
    }
}

Common Mistakes — Anti-Patterns

  • Sending commands over Kafka — the producer couples itself to a specific consumer, defeating the purpose of event-driven design.
  • Using a single shared consumer group — events are load-balanced and are not broadcast to all services that need them.
  • No compensation logic — the saga is stuck permanently in a partial state when any step fails.
  • Imperative event names (e.g., ProcessPayment) — ambiguous; the intent of the message is unclear to consumers.
  • No correlation ID propagated — logs across services cannot be linked to a single originating event or transaction.

Module 4 · Slide 1 — Multi-Service Event Flow & Failure Handling

What: Concise Technical Definition

Multi-service event flow is a series of Kafka events that trigger processing across multiple services, forming a saga. Failure handling distinguishes three distinct categories, each requiring a different response strategy:

  • Transient errors — temporary infrastructure failures (e.g., DB timeout, network blip); retry with exponential backoff.
  • Permanent errors — unrecoverable failures (e.g., malformed JSON, logic errors); route immediately to a Dead Letter Topic for manual review.
  • Business failures — valid but unsuccessful outcomes (e.g., out of stock, fraud detected); publish a compensating domain event, not an exception.

Retries must be non-blocking — they must not stall the partition or delay processing of other messages.

Why Does It Exist

In distributed systems, failures are inevitable. Without structured handling, transient glitches cause message loss, permanently bad data blocks entire partitions, and business failures are misclassified as technical errors — breaking sagas and leaving data in inconsistent states. A deliberate failure taxonomy ensures each failure type is resolved with the correct strategy.

When to Use It

  • Any saga where each service step can fail independently of the others.
  • Services experiencing intermittent infrastructure failures such as database timeouts or transient network errors.
  • To prevent a single malformed message from stalling an entire consumer group indefinitely.
  • To enable automated recovery for transient failures without requiring manual intervention.

Where to Use It

Consumer
Error handlers classify exceptions into transient, permanent, or business categories on receipt.
Retry Topics
Spring @RetryableTopic auto-creates retry and DLT topics with configurable backoff per exception type.
Database
Idempotency keys via database upserts prevent duplicate side effects from retried messages.
Operations
DLT recovery endpoints allow operators to inspect, fix, and replay failed messages to the original topic.

How to Implement — High-Level Steps

  1. Define an exception hierarchy: RetryableException, NonRetryableException.
  2. Configure @RetryableTopic with explicit include and exclude exception lists, and exponential backoff settings.
  3. Implement idempotent handlers using database upserts keyed on the business identifier.
  4. Propagate a correlation ID in Kafka message headers for end-to-end distributed tracing.
  5. Configure DLT topics with sufficient retention and expose a recovery API for operational replay.

Module 4 · Slide 3 — Failure Modes, Root Cause & Correct Approach

What Can Go Wrong — Failure Modes

  • Retrying permanent failures indefinitely — hammers downstream services with requests that can never succeed.
  • Business failures routed to the DLT — the saga loses the event and cannot trigger its compensating step.
  • No idempotency keys — retried messages execute their business logic multiple times, causing duplicate side effects.
  • No correlation ID — log entries across services cannot be linked; debugging a multi-hop failure is infeasible.
  • DLT configured with short retention — messages expire before the operations team can investigate and replay them.

Root Cause Analysis

  • Blind retry of all exceptions: Retrying a JSON parse error is a misclassification — it consumes the entire retry budget and will never succeed. The default behaviour of retrying all exceptions is rarely correct.
  • Business failure treated as a technical exception: Throwing a RuntimeException for a business rule violation (e.g., fraud detected) routes the event to the DLT rather than triggering the compensating saga step.
  • No idempotency key: Without a business-key-based upsert, a replayed message re-executes the state mutation, creating duplicate records or double-applied effects.
  • Missing headers: If the correlation ID is not propagated from producer to consumer headers on every hop, connecting log entries across services is impossible.

Correct Approach — Architectural Pattern

Structured Exception Classification and Recovery

  • Exception hierarchy: Define explicit base classes — RetryableException and NonRetryableException — and throw the appropriate type consistently.
  • @RetryableTopic with explicit lists: Use include for retryable types and exclude for permanent failure types; never rely on defaults.
  • Idempotent receivers: Implement database upserts using the business key (ON CONFLICT DO NOTHING) to make every handler safe to replay.
  • Correlation headers: Propagate X-Correlation-Id in all Kafka message headers from first publish through every downstream consumer.
  • DLT strategy: Configure long retention, set up alerting on DLT consumer lag, and expose a secure replay API for the operations team.

Key Principles

  • Idempotency: The same event processed multiple times must yield the same result — processing once or ten times is indistinguishable from the system's perspective.
  • Exponential backoff: Increasing delay between retry attempts prevents a thundering herd on services that are recovering from overload or transient failure.
  • Dead letter channel: Isolates unprocessable messages from the main processing flow without stalling the partition or affecting other consumers.
  • Observability: Trace IDs propagated in headers tie events across services into a queryable, correlated trace for debugging and audit.

Consumer with @RetryableTopic

@Component
public class InventoryEventHandler {

    @RetryableTopic(
        attempts = "4",  // original attempt + 3 retries
        backoff = @Backoff(delay = 2000, multiplier = 2.0, maxDelay = 30000),
        include = RetryableException.class,
        exclude = { JsonProcessingException.class, ValidationException.class },
        topicSuffixingStrategy = TopicSuffixingStrategy.SUFFIX_WITH_INDEX_VALUE
    )
    @KafkaListener(topics = "payment.created", groupId = "inventory-group")
    public void handle(String message, Acknowledgment ack) throws Exception {
        try {
            var event = om.readValue(message, PaymentCreatedEvent.class);
            repo.reserveIdempotent(event.orderId(), event.paymentId());
            ack.acknowledge();
        } catch (JsonProcessingException e) {
            throw new NonRetryableException("Malformed JSON", e);  // sent to DLT immediately
        } catch (DataAccessException e) {
            throw new RetryableException("DB timeout", e);          // retried with backoff
        }
    }

    @DltHandler
    public void onDlt(String message) {
        log.error("[DLT] Permanent failure — alerting operations: {}", message);
        // trigger alerting integration
    }
}

Common Mistakes — Anti-Patterns

  • No exception classification — all failures are retried; poison-pill messages loop through the retry chain indefinitely.
  • Business failures thrown as exceptions — fraud detection or stock exhaustion results end up in the DLT rather than triggering saga compensations.
  • Missing idempotency keys — duplicate events from retries execute business logic multiple times with unintended side effects.
  • No correlation ID propagated — log entries across services are unconnected; end-to-end debugging is impossible.
  • DLT with short retention — messages expire before the team can investigate and replay them.
